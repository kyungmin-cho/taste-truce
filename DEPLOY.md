# Deployment checklist

- Set server-side `QLOO_API_KEY`. Never include credentials in browser assets or images.
- Set `DEFAULT_SCENE=majority` for the public demo. The other values are `williamsburg` (used when unset) and `seongsu`.
- Mount a persistent writable volume at `/data` in the container. Cache and SQLite state must survive restarts; use one application instance with this local SQLite accounting model.
- Keep an instance running if the host otherwise scales to zero.
- The image runs `python prewarm.py` before starting the server; outside the image, run it yourself before serving traffic. It builds missing or expired snapshots for all three presets; existing snapshots require no calls. A prewarm failure is logged and the server starts anyway. Without a persistent volume every restart prewarms from an empty cache, so count those calls against the monthly budget. From a cold cache this takes 26 calls. `--refresh` rebuilds snapshots from the configured response cache and can make calls when that cache is missing or expired.
- Default response cache TTL is `QLOO_CACHE_TTL_SECONDS=0` (no expiry). Positive seconds configure response expiry. Default scene snapshots independently use `DEFAULT_SCENE_TTL_SECONDS=0`; a positive value must be at least `2592000` (30 days). A saved snapshot remains readable even when the response TTL expires.
- Daily cron example, inside the same runtime and environment with the same mounted volume: `0 4 * * * cd /app && python prewarm.py`. The image does not install or start cron; configure the host scheduler. Prewarming does not force-refresh an existing snapshot.
- Check `GET /health`: HTTP 200 with `status=ok`, `ready=true`, `needs_new_calls=false`, and a `saved_utc` value mean the configured default can be served without provider calls. If no usable snapshot exists it returns HTTP 503 with `status=not_ready` and `ready=false`, and prewarm is needed; underlying response cache hits may reduce the calls it needs. `GET /scene/default` returns 503 until ready. No GET starts a planner or calls Qloo.
- Set `COOKIE_SECURE=1` when serving over HTTPS. It adds `Secure` to the HttpOnly, SameSite=Strict session cookie. Local HTTP verification needs this unset or `0`.
- Behind a reverse proxy, set **both** `TRUSTED_PROXY_HEADER` (for example `CF-Connecting-IP`) and `TRUSTED_PROXY_IPS` (comma-separated immediate peer IPs or CIDR ranges such as `172.16.0.0/12`). Only those peers can supply the header; otherwise the socket peer is counted. `*` trusts every peer and is only safe when the platform proxy is the sole path to the application port (for example a managed Space). For `X-Forwarded-For`, the application uses its first value. The trusted proxy must overwrite/validate that header, and direct public access to the application must be blocked by host networking. Without these settings every visitor behind a proxy shares one IP and one set of daily limits.
- `IP_DAILY_SESSION_CAP` defaults to 20 per IP per UTC day. Only a session's first accepted POST consumes it; GETs and repeat POSTs in that session do not. An over-limit POST returns 429 while HTML, config, assets and saved scenes remain readable. `IP_DAILY_CALL_CAP` defaults to 100 uncached Qloo calls per IP per UTC day. SQLite preserves these limits across application restarts. Cookies are in memory and expire by `SESSION_TTL_SECONDS` (86400 default); a restart requires a fresh cookie.
- During a judging period, raise the per-visitor caps so testers are not cut off, for example `SESSION_CALL_CAP=100`, `IP_DAILY_SESSION_CAP=100` and `IP_DAILY_CALL_CAP=400`, and keep `MONTHLY_CALL_CAP` as the overall ceiling.
- Configure the host's public edge rate limiting separately. In-memory cookie slots (`MAX_SESSIONS`, default 1000) are bounded and can be evicted; the IP counters remain on disk.
- Set `LLM_BASE_URL` (OpenAI-compatible `/v1`), `LLM_MODEL`, and `LLM_API_KEY` for the planner and one observe/replan turn. Empty condition text skips the LLM. A failed/unconfigured LLM uses the local parser and deterministic next-step suggestions. Suggestions execute only after user selection. Do not configure a loopback development endpoint as a public deployment provider.
- Validate HTTPS cookie issuance, trusted client-IP behavior, first-POST limit, snapshot readiness, planner availability and restart persistence on the chosen host.
